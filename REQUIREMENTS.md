# Requirements register

One hundred and one requirements this project has been given — functional and
non-functional — in one place, with where each came from, whether it holds
today, and the evidence for that verdict. They were mined from nine commits, the
88 gap entries across the six area pages under `internal/ui/assets/docs/`, the
migrations that are the real contract, and three external findings that never
touched the code. Five rows came from reviewing the code while writing this file
and are in no other inventory: `API-02`, `API-09`, `SEC-08`, `OBS-09`, `OBS-10`.

The same register renders in the product, under **Docs → Requirements**
(`internal/ui/assets/docs/requirements.json`), beside the capability panel it
reconciles against.

There are three reasons this file exists rather than the requirements living in
commit messages, in the six area pages under the Docs tab, and in a research
folder nobody opens.

The first is that a requirement and a gap are the same object seen from two
sides. The Docs tab documents 88 gaps beautifully and never says what any of
them was supposed to be doing. "The fence is not enforced at the resource" is
only legible next to "a fenced holder must not be able to reach the device".

The second is that the origin matters as much as the status. A requirement that
came out of an incident in somebody else's system (STF #663), a requirement that
came out of a supplier's acceptable-use policy, and a requirement that came out
of a fire-test paper are three different kinds of obligation, and they decay
differently. A contract clause changes when the supplier changes it. A physics
result does not.

The third is that a status claim is worthless without the command that produced
it. Every status below was checked against this tree. Where the check is a
one-liner, the one-liner is in the row.

## Last re-verified

Against `HEAD`, 2026-09-04. **Thirty-six rows moved**, and the reason is worth stating because it is a property of a register rather than an accident: this file was written on a tree that did not yet contain migration `00005`, the two commits that closed the blocking gaps, or the nine branches that were open when it was written. A status column is a claim about a tree, and it decays the moment the tree moves. Thirteen rows became `met`, four became `linux_only` (built, reachable only from a Linux host, and never observed there), one became `decided` and the rest had their evidence corrected while keeping their status.

The single largest cause was `OPS-04`. It predicted that making `farmd node` startable would unblock four rows and cost one guard; it did, and they are `DEV-04`, `DEV-05`, `REC-03` and `HW-06`. The row that had to be *reopened* is none of them: `LEASE-09` went from `not_built` to `partial` because a witness loop and an on-device marker were both built and nothing starts either, which is a more specific and more embarrassing state than absence.

Every moved row names the file or migration that moved it, so a reader can re-run the check rather than trust the verdict.

## Status vocabulary

| Status | Meaning |
|---|---|
| `met` | Implemented, and demonstrated to work. |
| `partial` | Implemented, with a named hole. The row names it. |
| `not_built` | Nothing in the tree implements it. |
| `linux_only` | Implemented, reachable only on Linux — and not reachable in any deployment that ships today. |
| `unverified` | Implemented and plausibly correct, never observed working. |
| `decided` | Raised, answered by a decision rather than by code. No implementation is owed. |

`met` is the only status that means "stop reading". Everything else is a
liability with a name.

## How to read an ID and an origin

IDs are `AREA-NN`. The area is where the requirement lives, not where it is
violated: the fence-at-the-resource requirement is `SEC-04` even though its
absence is felt most in the lease protocol.

Origins:

| Origin | What it is |
|---|---|
| `c:<sha>` | A commit whose message raises or closes the requirement. |
| `gap:<area>.<n>` | Entry *n* of the `gaps` array in `internal/ui/assets/docs/<area>.json`. |
| `README` | A claim in README.md that an operator will read as a promise. |
| `cap:features` | An entry in `featureStatuses()` in `internal/api/capabilities.go`. |
| `schema` | The migration is the contract; the column or constraint is the requirement. |
| `research:*` | An external finding — a supplier contract, a fire-test result, a code table. |

## A note on what "verified" means here

Statuses in this file were checked three ways, in descending order of strength:
executed against a live farm (those checks are the ones the six area pages
carry, 304 examples of them); executed as a grep or a build against this tree;
or read from the code. Where a row says `not_built` because a symbol has no
caller, the grep is in the row and you can re-run it. Where a row says
`unverified`, nobody has watched it work and the row says so rather than
inheriting confidence from the code being tidy.

Two structural facts worth stating once, because several rows depend on them:

- **The demo is not the system.** `internal/demo` writes `farm.device_runtime`,
  `farm.recovery_attempts`, `farm.quarantines`, `farm.events` and `farm.jobs.state`
  with its own rules. Rows attributed to the demo prove the schema works and
  prove nothing about the loop whose job it is.
- **Nothing runs as its own Postgres role.** `farm_reaper`, `farm_scheduler` and
  `farm_watchdog` are created `NOLOGIN`, and every process connects with one
  `DATABASE_URL`. The role firewall is correct DDL that no deployment assumes.

## Reconciling `featureStatuses()`

`internal/api/capabilities.go` hand-maintains a twelve-entry feature list, rendered at the top of this page as **What is enabled, and how**. Six entries compute their state from a heartbeat; six are hardcoded. It is the most-read status surface in the product, so where it disagrees with this register, that is a defect in the list rather than a difference of opinion.

The three defects that belonged to the panel itself are closed: it is gated at the tenant role like every other route (SEC-08), and it reports a failed probe as a 503 naming what it could not observe instead of answering 200 with a schema of v0 and an empty fleet (OBS-09). Reading `goose_db_version` directly rather than `cfg.MigrationsTable` (OBS-10) remains.

## What the register argues for next

Ordered by unblocked-per-unit-of-work, not by severity. Six of the previous ten are done, and the shape of what is left has changed with them: the cheap call sites for expensive, already-written machinery are nearly exhausted, and what remains is mostly work that has to be built rather than connected. One exception leads the list, and it is the most important row in the register.

1. **`LEASE-09` — start the witness loop.** The loop is written, the on-device marker that feeds it is written, the SQL function is written, the config is validated, and every `StartWitness` call site in the tree is a test. This is the last unwired half of the countermeasure the whole project is built around: without it, a control-plane outage longer than TTL+grace still takes a working job's device away, which is #663 arriving by a different road. One call site in the jobrunner.

2. **`LEASE-11` — an operator-reachable kill switch for the reaper.** `farm.reaper_state.enabled` is read on every `lease_reclaim` and written by no route, no `ctl` command and no dashboard control. Turning off the only automatic release path during an incident is currently a hand-written UPDATE with no audit row — at exactly the moment you least want an unlogged change.

3. **`REC-12` — exclude quarantined and unhealthy devices from bulk selection.** `expandBulkSelector` treats health as a filter the caller may add rather than an exclusion. Harmless for a `getprop`; a `reboot` across a quarantined hub produces a wave of failures and an error rate that means nothing.

4. **`DEV-02` — make `resolve_device` rung 3 answer `ambiguous`.** It sets the verdict and leaves `v_dev` NULL, and rung 4 tests only `IF v_dev IS NULL`, so a clone serial in an empty slot is reported to the caller as adopted rather than flagged. This moved UP the list when OPS-04 closed: enrollment can now actually run, so the wrong answer is reachable rather than theoretical.

5. **The charge-policy loop (`HW-03`, `DEV-09`).** Both things it needed now exist — the battery reader writes `battery_pct`, and the parked state means a device held dark on purpose is not mistaken for a fault and quarantined. What is left is the loop itself and a charge gate the agent can hold, which `portPower` cannot: it arms a deferred power-on by construction, which is right for recovery and incompatible with keeping a port dark for hours. This is the only row where a physical safety mitigation is waiting on software.

6. **`SEC-04` — the fence proxy.** The fence is enforced in PostgreSQL and HONOURED by the client; nothing enforces it at the resource, so a misbehaving client still reaches a device it has been fenced out of. The largest remaining item, and the only one that changes the architecture. The revoke response body already claims this exists.

7. **`JOB-06`/`JOB-07` — write `profile_id` and its three siblings from the API.** Until then every reset between tenants is a green step that expands to nothing.

8. **`OBS-08` — a `PrometheusRule` and runbooks for the lease paths.** The counters are exported now (OBS-02) and nothing alerts on them. "Hold and page" is still a WARN line with no pager on the other end, which is the one behaviour that is supposed to wake a human.

9. **`SEC-07` — scope the six unscoped read surfaces.** `/events` is closed; `/fleet`, `/topology`, `/hosts`, `/recovery`, `/bulk` and `/stream` are not. The stream needs a poller per tenant and is the reason this is not a one-liner.

10. **`TEST-04`/`TEST-05` — a test for `isRetryable` and `planResume`.** A regression in either reintroduces #663, which is the failure this project defines itself against. The `leaseOps` interface exists so a stub can drive the branch its own doc comment calls the single most consequential decision in the project, and nothing drives it.
